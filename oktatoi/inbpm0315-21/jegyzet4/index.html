Öröklés, túlterhelés, felülírás, polimorfizmus

Magas szintű programozási nyelvek 2 (INBPM0315-21) · 4. labor gyakorlat · Frissítve: 2026-09-19

Tematika

  • Öröklés (extends, super)
  • Láthatóság: protected
  • Metódus túlterhelés (overloading)
  • Metódus felülírás (overriding)
  • Polimorfizmus

Kontextus

A múlt órán felépítettük a Student osztályt: névvel, Neptun-kóddal, jegyekkel. Ma tegyük fel, hogy szükségünk van egy speciális hallgatóra is — mondjuk egy diplomamunkás hallgatóra, akinek mindene megvan, amije egy Student-nek, plusz van egy témavezetője és egy diplomamunka-témája is.

Megtehetnénk, hogy lemásoljuk a Student teljes kódját egy új osztályba, és hozzáadjuk az új mezőket — de ez kódduplikáció, és ha a Student-en változtatunk, mindenhol külön kellene javítani. Erre a problémára ad megoldást az öröklés.

Hirdetés

Öröklés

Öröklés (inheritance): Az öröklés lehetővé teszi, hogy egy osztály átvegye egy másik osztály mezőit és metódusait, és csak a különbségeket adja hozzá. 

public class GraduateStudent extends Student {
    protected String supervisor;
    protected String thesisTopic;

    public GraduateStudent(String name, String neptunCode, int[] grades,
                            String supervisor, String thesisTopic) {
        super(name, neptunCode, grades);
        this.supervisor = supervisor;
        this.thesisTopic = thesisTopic;
    }
}

Amit tisztázni kell:

  • extends: a GraduateStudent extends Student azt jelenti, hogy a GraduateStudent egy Student is, plusz extra képességekkel. A Student-et itt szülőosztálynak (superclass), a GraduateStudent-et leszármazott osztálynak (subclass) nevezzük.
  • super(...): a leszármazott osztály konstruktorának első sorában meg kell hívnunk a szülő konstruktorát, hogy az beállítsa az öröklött mezőket (name, neptunCode, grades). A super(...) pontosan ezt teszi.
  • A GraduateStudent automatikusan megkapja a Student összes public/protected mezőjét és metódusát (pl. getAverage()) — ezeket nem kell újra megírni.
GraduateStudent g = new GraduateStudent(
    "Kiss Réka", "GHI789", new int[]{5, 5, 4},
    "Dr. Nagy Péter", "Gépi tanulás alkalmazásai"
);

System.out.println(g.getAverage());   // öröklött metódus, működik simán

Láthatóság: protected

Emlékeztető az előző óráról: private — csak az adott osztályon belülről érhető el; public — bárhonnan elérhető. Ha a Student mezői (name, neptunCode, grades) private-ok lennének, a GraduateStudent nem férne hozzájuk közvetlenül — pedig logikailag "családon belül vagyunk".

protected: A protected mező/metódus elérhető az adott osztályon belülről, és a leszármazott osztályokból is (akkor is, ha azok más csomagban vannak), de kívülről (nem-leszármazott osztályokból) nem. 

public class Student {
    protected String name;
    protected String neptunCode;
    protected int[] grades;

    // ...
}

Ezért írtuk a Student mezőit protected-re — így a GraduateStudent konstruktora (a super(...) híváson keresztül) és bármelyik jövőbeli leszármazott hozzáférhet hozzájuk.

Megjegyzés: a valós, "védekező" kódolási stílusban gyakran inkább private mezőket tartunk a szülőosztályban is, és protected/public gettereken/settereken keresztül engedünk hozzáférést a leszármazottaknak — így a szülőosztály teljes kontrollt tart a saját állapota felett. Ma a fogalom tisztasága kedvéért közvetlenül protected mezőket használunk, de éles kódban érdemes megfontolni a getteres/setteres változatot is.

Metódus túlterhelés (overloading)

Túlterhelés (overloading): Ugyanabban az osztályban több metódus (vagy konstruktor) is viselheti ugyanazt a nevet, ha a paraméterlistájuk különbözik (más számú vagy más típusú paraméter). 

public class Student {
    // ...

    public void addGrade(int newGrade) {
        int currentGradeLength = this.grades.length;
        int newGradeLength = currentGradeLength + 1;
        int[] newGrades = new int[newGradeLength];

        for (int i = 0; i < currentGradeLength; ++i) {
            newGrades[i] = this.grades[i];
        }

        newGrades[newGradeLength - 1] = newGrade;

        this.setGrades(newGrades);
    }

    public void addGrade(int newGrade, String comment) {
        this.addGrade(newGrade);
        System.out.println("Megjegyzés a jegyhez: " + comment);
    }
}

Mindkét metódus neve addGrade, de a fordító a paraméterek száma/típusa alapján tudja eldönteni, melyiket hívjuk. Ez nem ugyanaz, mint a felülírás — a túlterhelés ugyanabban az osztályban történik, és a metódus viselkedése teljesen új, nincs "felülírt" kapcsolat egy szülőosztály metódusával.

Hirdetés

Metódus felülírás (overriding)

Felülírás (overriding): Egy leszármazott osztály újraírhatja egy örökölt metódus viselkedését, ugyanazzal a névvel és paraméterlistával.

Adjunk a Student-hez egy describeStudent() metódust:

public class Student {
    // ...

    public String describeStudent() {
        return this.getName() + " (" + this.getNeptunCode() + "), átlag: " + this.getAverage();
    }
}

A GraduateStudent írja felül, hogy a témavezetőt és a témát is megjelenítse: 

public class GraduateStudent extends Student {
    // ...

    @Override
    public String describeStudent() {
        return super.describeStudent() + ", temavezeto: " + this.getSupervisor() + ", tema: " + this.getThesisTopic();
    }
}

Amit tisztázni kell:

  • @Override: jelzi (és a fordítóval ellenőrizteti), hogy szándékosan írjuk felül a szülőosztály egy metódusát — ugyanazt láttuk már az equals()-nál a múlt órán.
  • super.describeStudent(): meghívja a szülőosztály eredeti describeStudent() implementációját, és ahhoz fűzzük hozzá az új, GraduateStudent-specifikus részt — így nem duplikáljuk a szülő logikáját, csak kibővítjük.

Túlterhelés vs. felülírás — a leggyakoribb keveredés: a túlterhelés ugyanabban az osztályban, különböző paraméterlistával hoz létre több változatot egy névből; a felülírás egy leszármazott osztályban, ugyanazzal a paraméterlistával cseréli le egy örökölt metódus viselkedését.

Polimorfizmus

Polimorfizmus: Azt jelenti, hogy egy szülőosztály típusú változó mögött ténylegesen egy leszármazott osztály példánya is állhat, és a metódushívás a tényleges típus szerinti viselkedést váltja ki — nem a változó deklarált típusa szerintit. 

Student s = new GraduateStudent(
    "Kiss Réka", "GHI789", new int[]{5, 5, 4},
    "Dr. Nagy Péter", "Gépi tanulás alkalmazásai"
);

System.out.println(s.describeStudent());

Bár s deklarált típusa Student, a describeStudent() hívás a GraduateStudent felülírt verzióját futtatja le, mert az s mögötti valódi objektum egy GraduateStudent. Ezt hívjuk upcastingnak (a leszármazottat a szülő típusaként kezeljük) — és emiatt működik a polimorfizmus.

Miért hasznos ez? — egy vegyes tömb

Emlékezzetek a 2. óra tömbjeire: egy tömb elemei azonos típusúak — de mivel a GraduateStudent is egy Student, egy Student[] tömbben mindkét fajta objektum elfér: 

Student[] students = new Student[3];
students[0] = new Student("Kovács Anna", "ABC123", new int[]{5, 4, 5});
students[1] = new GraduateStudent("Kiss Réka", "GHI789", new int[]{5, 5, 4},
                                   "Dr. Nagy Péter", "Gépi tanulás alkalmazásai");
students[2] = new Student("Nagy Béla", "XYZ789", new int[]{3, 4, 2});

for (Student current : students) {
    System.out.println(current.describeStudent());
}

A ciklus törzse egyáltalán nem tudja (és nem is kell tudnia), hogy éppen egy Student-tel vagy egy GraduateStudent-tel dolgozik — mindegyik elemen meghívja a describeStudent()-ot, és mindegyik a saját, tényleges típusának megfelelő változatot futtatja le. Ez a polimorfizmus gyakorlati haszna: egységesen tudunk kezelni különböző, de rokon típusú objektumokat.

Gyakorlat

  1. Adjatok a GraduateStudent-hez egy újabb felülírt metódust (pl. getAverage() felülírása úgy, hogy a diplomamunka-jegyet is beleszámítsa az átlagba, super.getAverage() felhasználásával).
  2. Írjatok egy újabb túlterhelt addGrade változatot a Student-ben (pl. dátummal), és hívjátok meg mindkét (vagy mindhárom) verziót.
  3. Hozzatok létre egy Student[] tömböt, amiben legalább 2 Student és 2 GraduateStudent objektum van vegyesen, és írjátok ki mindegyikre a describeStudent() eredményét egy ciklussal.
  4. Debuggerrel (2. óra!) lépegessetek végig a ciklus egy GraduateStudent-elemén, és nézzétek meg, hogyan "ugrik be" a describeStudent() hívásnál a felülírt (nem az eredeti) implementáció.

Házi feladat

Ezek a feladatok a 4. órán tanultak (öröklés, protected, túlterhelés vs. felülírás, polimorfizmus) önálló, otthoni elmélyítésére szolgálnak, a Student/GraduateStudent hierarchiátokra építve.

1. feladat (Könnyű) — Új leszármazott: PartTimeStudent

Hozzatok létre egy PartTimeStudent extends Student osztályt, egy extra int workHoursPerWeek mezővel (heti munkaóra). A konstruktorban hívjátok meg a super(...)-t a Student mezőinek beállításához, majd állítsátok be a saját mezőt is.

2. feladat (Közepes) — Túlterhelt konstruktor

Vegyetek fel a Student osztályba egy második, túlterhelt konstruktort, amely csak a name-et és a neptunCode-ot várja paraméterként (jegyek nélkül), és belül egy üres int[0] tömböt állít be grades-nek. Ellenőrizzétek, hogy getAverage() meghívása egy így létrehozott hallgatón nem dob-e hibát (gondoljátok át: mi történik 0 hosszú tömb esetén az átlagszámításnál — ha hibát találtok, ez rendben van, ez a feladat pont erre a felfedezésre irányul).

3. feladat (Közepes/Haladó) — Felülírás és polimorfizmus a PartTimeStudent-en

Írjatok egy describeStudent() felülírást a PartTimeStudent-be, amely a super.describeStudent() eredményéhez hozzáfűzi a heti munkaóra számát. Hozzatok létre egy vegyes Student[] tömböt (Student, GraduateStudent, PartTimeStudent keverve), és írjátok ki mindegyik describeStudent()-ját egy ciklussal.

4. feladat (Haladó) — Jósold meg a kimenetet

Az alábbi kódrészlet túlterhelést és felülírást is tartalmaz. Mielőtt lefuttatnátok, írjátok le papírra, mit vártok, hogy kiírjon a program — utána futtassátok le, és ellenőrizzétek magatokat. 

public class Base {
    public String greet() {
        return "Base.greet()";
    }

    public String greet(String name) {
        return "Base.greet(String) - " + name;
    }
}

public class Derived extends Base {
    @Override
    public String greet() {
        return "Derived.greet()";
    }
}

public class Main {
    public static void main(String[] args) {
        Base b = new Derived();
        System.out.println(b.greet());
        System.out.println(b.greet("Anna"));
    }
}

A három osztályt külön fájlba tegyétek (Base.java, Derived.java, Main.java) — fájlonként csak egy public osztály lehet.

Gondolkodjatok el rajta: miért ugyanaz a viselkedés az első hívásnál, mint amit a polimorfizmusnál tanultunk, míg a második hívásnál nincs is felülírt verzió a Derived-ben — mégis lefordul és lefut a kód. Miért?
