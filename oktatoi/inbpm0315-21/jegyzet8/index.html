Kontextus

A 2. órán már láttatok egy programot összeomlani: a szándékosan elrontott ciklus ArrayIndexOutOfBoundsException-t dobott, és a program futása azonnal megszakadt. A Scanner.nextInt() is hasonlóan viselkedik, ha valaki szöveget gépel be szám helyett — InputMismatchException-nel áll le. Ma megtanuljuk, hogyan kezeljük ezeket a helyzeteket szándékosan, ahelyett hogy hagynánk a programot összeomlani — és hogyan írjunk saját kivételt a Student hierarchiánkhoz.

Hirdetés

Kivétel alapok: try-catch

Kivétel (exception): Egy kivétel egy objektum, amely azt jelzi, hogy futás közben valami rendellenes történt — és amely, ha nem kezeljük, megszakítja a program normális futását.

Idézzük fel a 2. óra hibáját, de most kezeljük le:

int[] grades = {5, 4, 5};

try {
    System.out.println(grades[5]);   // nincs 6. elem, ArrayIndexOutOfBoundsException
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Hibás index! Üzenet: " + e.getMessage());
}

System.out.println("A program folytatódik.");

Amit tisztázni kell:

  • try { ... }: az a kódrész, amelyben egy esetlegesen dobódó kivételre számítunk.
  • catch (Típus e) { ... }: ha a try blokkban a megadott típusú (vagy annak leszármazott) kivétel keletkezik, ide ugrik a vezérlés — a program nem áll le, hanem itt folytatódik.
  • e.getMessage(): a kivétel objektum egy metódusa, amely egy szöveges leírást ad a hibáról.
  • A try/catch blokk után a program normálisan folytatódik — ez a legfontosabb különbség a kezeletlen kivételhez képest, ami a 2. órán a teljes programot leállította.

Checked vs. unchecked kivételek

Minden kivétel a Throwable osztályból származik, ezen belül két nagy ágra oszlik:

Unchecked (nem ellenőrzött) kivétel: A RuntimeException (és leszármazottai, pl. ArrayIndexOutOfBoundsException, InputMismatchException, NullPointerException) leszármazottja. A fordító nem kényszerít minket arra, hogy kezeljük vagy deklaráljuk — a program simán lefordul akkor is, ha nincs try/catch körülötte, csak futás közben, ha bekövetkezik, összeomlik a program.

Checked (ellenőrzött) kivétel: Az Exception leszármazottja, de nem a RuntimeException-é. A fordító kikényszeríti, hogy vagy try/catch-csel kezeljük, vagy a metódus fejlécében throws-szal jelezzük, hogy továbbadjuk — enélkül a kód nem fordul le. 

Throwable
├── Exception                     (checked — kivéve a RuntimeException ágat)
│   ├── IOException                (checked — jövő héten találkozunk vele)
│   └── RuntimeException           (unchecked)
│       ├── ArrayIndexOutOfBoundsException
│       ├── InputMismatchException
│       └── NullPointerException
└── Error                         (súlyos, JVM-szintű hibák — ritkán kezeljük)

A jövő héten meg fogjátok látni, hogy fájlkezeléskor az IOException egy checked kivétel — pontosan emiatt fogja a fordító megkövetelni, hogy minden fájlműveletet try/catch-csel vagy throws-szal kezeljetek.

Hirdetés

finally, több catch ág

finally: A finally blokk mindig lefut — akár volt kivétel, akár nem, akár return volt a try-ban. Jellemzően "takarítási" műveletekhez használjuk (pl. erőforrás lezárása — erre jövő héten látunk valódi példát fájlokkal). 

try {
    System.out.println(grades[5]);
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Hibás index!");
} finally {
    System.out.println("Ez mindig lefut.");
}

Több catch ág: Egy try blokkhoz több catch ág is tartozhat, különböző kivételtípusokra — a specifikusabb típust mindig az általánosabb elé kell írni, különben a fordító hibát jelez (a specifikusabb ág soha nem futna le). 

try {
    int[] numbers = {1, 2, 3};
    System.out.println(numbers[5] / 0);
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Hibás index: " + e.getMessage());
} catch (ArithmeticException e) {
    System.out.println("Nullával osztás: " + e.getMessage());
} catch (Exception e) {
    System.out.println("Valami más hiba történt: " + e.getMessage());
}

Saját kivétel: InvalidGradeException

Eddig csak beépített kivételeket fogtunk el. Most írjunk egy sajátot: a Student osztályba felvett jegyeknek 1 és 5 közé kell esniük — ha valaki érvénytelen jegyet próbál megadni, ezt egy dedikált kivétellel jelezzük, nem csak egy általános IllegalArgumentException-nel. 

public class InvalidGradeException extends Exception {
    public InvalidGradeException(String message) {
        super(message);
    }
}

Mivel az Exception-ből (és nem a RuntimeException-ből) származtatjuk, ez egy checked kivétel — a fordító mindenhol meg fogja követelni a kezelését, ahol dobható.

Vezessük be a validációt a Student konstruktorába:

public class Student {
    // ...

    public Student(String name, String neptunCode, int[] grades) throws InvalidGradeException {
        for (int grade : grades) {
            if (grade < 1 || grade > 5) {
                throw new InvalidGradeException("Érvénytelen jegy: " + grade + " (1 és 5 között kell lennie)");
            }
        }
        this.name = name;
        this.neptunCode = neptunCode;
        this.grades = grades;
    }
}

Fontos, azonnali következmény: mivel a konstruktor most már throws InvalidGradeException-t deklarál, minden eddigi new Student(...) hívásunk (az összes korábbi óránkban!) mostantól nem fordul le kezelés nélkül. Két lehetőségünk van: 

// 1. lehetőség: try/catch a hívás körül
try {
    Student anna = new Student("Kovács Anna", "ABC123", new int[]{5, 4, 5});
    System.out.println(anna.getAverage());
} catch (InvalidGradeException e) {
    System.out.println("Nem sikerült létrehozni a hallgatót: " + e.getMessage());
}

// 2. lehetőség: throws továbbadása (pl. ha a main-ben vagyunk, és ott akarjuk kezelni)
public static void main(String[] args) throws InvalidGradeException {
    Student anna = new Student("Kovács Anna", "ABC123", new int[]{5, 4, 5});
    System.out.println(anna.getAverage());
}

Ez a legjobb, kézzelfogható bizonyíték arra, mit is jelent valójában a "checked" jelző: a fordító kényszerít minket a hiba explicit kezelésére, még mielőtt a program egyáltalán lefutna.

Gyakorlat

  1. Fogjátok el az InputMismatchException-t egy Scanner.nextInt() hívás körül (2. óra) — ha a felhasználó szöveget ír be szám helyett, írjatok ki egy barátságos hibaüzenetet ahelyett, hogy a program összeomlana.
  2. Adjatok egy hasonló validációt egy másik mezőhöz is (pl. a name ne lehessen üres) — dönthettek úgy, hogy ez unchecked (IllegalArgumentException) vagy checked (saját, Exception-ből származó) kivételt dob; indokoljátok a választást.
  3. Írjatok egy JUnit tesztet (7. óra) assertThrows-zal, amely ellenőrzi, hogy egy 6-os "jegy" megadásakor InvalidGradeException keletkezik: 
    import org.junit.jupiter.api.function.Executable;
import static org.junit.jupiter.api.Assertions.assertThrows;

@Test
void invalidGradeThrowsException() {
    assertThrows(InvalidGradeException.class, new Executable() {
        @Override
        public void execute() throws Throwable {
            new Student("X", "Y", new int[]{6});
        }
    });
}

    (A rövidebb, lambdás forma majd a 10. órán kerül elő — most szándékosan az explicit Executable megvalósítást használjuk.)

  4. Vizsgáljátok meg debuggerrel (2. óra!): tegyetek egy breakpointot az InvalidGradeException throw sorára, és nézzétek meg lépésről lépésre, hogyan "ugrik ki" a vezérlés a catch ágba.

Megoldások

1. feladat

import java.util.InputMismatchException;
import java.util.Scanner;

Scanner scanner = new Scanner(System.in);
System.out.print("Hány éves vagy? ");

try {
    int age = scanner.nextInt();
    System.out.println("Kor: " + age);
} catch (InputMismatchException e) {
    System.out.println("Ez nem egy érvényes szám volt! Egész számot adj meg.");
}

Ha a felhasználó szöveget gépel be ("huszonöt" helyett 25-öt várva), a nextInt() InputMismatchException-t dob — ezt fogjuk el, ahelyett hogy a program összeomlana.

2. feladat

A name mezőre már van validáció a 3. óráról (setName(), unchecked IllegalArgumentException) — válasszunk egy másik, még nem validált mezőt: a neptunCode legyen pontosan 6 karakter hosszú. 

public class InvalidNeptunCodeException extends Exception {
    public InvalidNeptunCodeException(String message) {
        super(message);
    }
}
public void setNeptunCode(String neptunCode) throws InvalidNeptunCodeException {
    if (neptunCode == null || neptunCode.length() != 6) {
        throw new InvalidNeptunCodeException("A Neptun-kódnak pontosan 6 karakterből kell állnia: " + neptunCode);
    }
    this.neptunCode = neptunCode;
}

Indoklás: ez szándékosan checked kivétel, szemben a setName() unchecked IllegalArgumentException-jével — jó alkalom a kettő összehasonlítására. A Neptun-kód formátuma egy domain-specifikus, várható hiba (hasonlóan az InvalidGradeException-hez), amit érdemes explicit módon kikényszeríteni a hívó kódra — szemben a setName()-nél látott, inkább "ez sosem kellene, hogy előforduljon" jellegű, programozói hibára emlékeztető esettel, ahol az unchecked forma volt indokolt.

3. feladat

Ennek a feladatnak a megoldása már teljes egészében szerepel a feladat szövegében (a assertThrows + Executable kód fentebb) — nincs mit hozzátenni, a feladat lényege pontosan az volt, hogy lássátok, hogyan tesztelhető egy checked kivétel dobása JUnit-tal.

4. feladat

Ez a feladat a debuggeren keresztül figyelendő meg, nincs önálló "megoldó" kód:

  • Tegyetek egy breakpointot a throw new InvalidGradeException(...) sorra (a Student konstruktorában), és hozzatok létre egy Student-et érvénytelen jeggyel (pl. 6) Debug módban.
  • A program megáll a throw sornál, mielőtt a kivétel objektum "elindulna".
  • Step Over-rel (vagy Step Into-vel) tovább lépve figyeljétek meg: a vezérlés nem a throw utáni sorra megy (nincs is olyan, hiszen a konstruktor további sorai — this.name = name; stb. — ilyenkor nem futnak le), hanem egyenesen a hívó kódban lévő, megfelelő catch (InvalidGradeException e) ág elejére ugrik.
  • Ez konkrétan megmutatja, mit jelent a "kivétel dobása": a normális, soronkénti végrehajtás megszakad, és a vezérlés a legközelebbi, megfelelő típusú catch ághoz "ugrik", útközben kihagyva mindent, ami a try blokkban még hátra volt.

Házi feladat

Ezek a feladatok a 8. órán tanultak (try/catch/finally, checked vs. unchecked kivételek, saját kivétel) önálló, otthoni elmélyítésére szolgálnak.

1. feladat (Könnyű) — Nullával osztás elkapása

Írjatok egy getAverageAsInt() metódust a Student-hez, amely egész osztással (int sum / grades.length, tehát nem double-lé alakítva) számolja ki az átlagot. Hívjátok meg egy olyan Student-en, akinek a grades tömbje üres (new Student("X", "Y", new int[0])), try/catch-csel fogva el az ArithmeticException-t. (Ne feledjétek: a konstruktor checked InvalidGradeException-t is deklarál, tehát arra is kell egy catch ág, még akkor is, ha üres tömb esetén ez sosem dobódik ténylegesen.) Hasonlítsátok össze: miért kivételt dob ez, míg a 4. órán az üres tömbös double-ös átlag csak NaN-t adott vissza, kivétel nélkül?

2. feladat (Közepes) — Saját unchecked kivétel

Vegyetek fel a Student osztályba egy új int semesterNumber mezőt (hányadik félévében jár a hallgató), és írjatok hozzá egy NegativeSemesterException extends RuntimeException kivételt — a setterében (vagy a konstruktorban) negatív érték esetén dobjon kivételt.

Gondolkodjatok el rajta, és írjátok le indoklással: miért unchecked ez a kivétel, míg az órán megismert InvalidGradeException checked? Mi indokolhatja a különböző választást a két esetben?

3. feladat (Közepes/Haladó) — Több kivételtípus egy catch ágban

Írjatok egy parseAndValidateGrade(String text) metódust, amely egy szöveget egész számmá alakít (Integer.parseInt, ami NumberFormatException-t dobhat, ha a szöveg nem szám), majd ellenőrzi, hogy 1–5 közé esik-e (ha nem, dobjon InvalidGradeException-t). Hívjátok meg ezt a metódust egy egyetlen, több típust kezelő catch ággal (catch (InvalidGradeException | NumberFormatException e)), amely mindkét esetben ugyanazt a barátságos hibaüzenetet írja ki.

4. feladat (Haladó) — Garantált "lezárás" finally-val

Írjatok egy egyszerű SimulatedConnection osztályt open() és close() metódusokkal (csak System.out.println-nel jelezzék, hogy megnyíltak/bezárultak), és egy doRiskyWork() metódust, amely néha (pl. egy paraméter alapján) RuntimeException-t dob. Írjatok egy try/finally blokkot úgy, hogy a close() mindig lefusson, akkor is, ha a doRiskyWork() kivételt dob.
